# 18.4 Istio Mesh Upgrade Cheat Sheet (ICA Exam Guide)

Upgrading Istio safely is a core topic tested on the **Istio Certified Associate (ICA)** exam. This cheat sheet covers the exact commands, workflow steps, revision tags, gateway strategies, and compatibility flags needed to pass ICA exam questions on Istio upgrades.

---

## 1. Quick Exam Reference Matrix

| Task | Command / Action | Key Exam Notes |
| :--- | :--- | :--- |
| **Upgrade Precheck** | `istioctl x precheck` | Always run **BEFORE** installing a new control plane. |
| **Check Revision Compatibility** | `istioctl x precheck --from-version 1.25.0` | Checks for breaking changes between versions. |
| **Install Canary Control Plane** | `istioctl install --set revision=1-26-3 -y` | Keeps old control plane running side-by-side. |
| **List Installed Revisions & Tags** | `istioctl tag list` | Displays active tags, revisions, and mapped namespaces. |
| **Create Revision Tag** | `istioctl tag set prod-stable --revision 1-25-0` | Maps a stable alias tag to a specific revision. |
| **Point Tag to New Revision** | `istioctl tag set prod-stable --revision 1-26-3 --overwrite` | Instantly migrates all tagged namespaces to the new `istiod`. |
| **Migrate Namespace Workloads** | `kubectl rollout restart deployment -n <ns>` | Forces Envoy sidecars to re-inject with the new version. |
| **Verify Proxy Version** | `istioctl proxy-status` or `istioctl version` | Verifies data plane proxy version matches control plane. |
| **Uninstall Old Control Plane** | `istioctl uninstall --revision 1-25-0 -y` | Cleanly removes old `istiod` without affecting new workloads. |

## 2. In-Place vs. Canary Upgrades (Exam Theory)

### In-Place Upgrade (NOT Recommended for Production)
* **Command:** `istioctl install -f new-config.yaml` (without `revision` flag).
* **Behavior:** Overwrites existing `istiod` deployment directly in `istio-system`.
* **Risk:** High. If the new `istiod` fails or introduces breaking changes, the entire mesh control plane goes down.

### Canary Upgrade (Istio & ICA Exam Standard)
* **Command:** `istioctl install --set revision=1-26-3 -f new-config.yaml`
* **Behavior:** Deploys a **new side-by-side `istiod-1-26-3` pod** in `istio-system`.
* **Advantage:** Zero downtime. Allows gradual namespace-by-namespace data plane migration. Rollback is as simple as switching labels/tags back.

```
                  ┌─────────────────────────────────────────┐
                  │ istio-system Namespace                  │
                  │                                         │
                  │  ┌───────────────────────────────────┐  │
                  │  │ istiod-1-25-0 (Old Revision)       │  │
                  │  └─────────────────┬─────────────────┘  │
                  │                    │                    │
                  │  ┌─────────────────▼─────────────────┐  │
                  │  │ istiod-1-26-3 (New Canary Rev)    │  │
                  │  └─────────────────┬─────────────────┘  │
                  └────────────────────┼────────────────────┘
                                       │
            ┌──────────────────────────┴──────────────────────────┐
            ▼                                                     ▼
┌─────────────────────────┐                           ┌─────────────────────────┐
│ Namespace: app-v1       │                           │ Namespace: app-v2       │
│ Label:                  │                           │ Label:                  │
│ istio.io/rev=1-25-0     │                           │ istio.io/rev=1-26-3     │
│ (Connected to Old)      │                           │ (Connected to Canary)   │
└─────────────────────────┘                           └─────────────────────────┘
```

## 3. Step-by-Step Canary Upgrade Workflow (Command Sequence)

### Step 1: Run Precheck
```bash
# Check cluster health and potential upgrade blockers
istioctl x precheck

# Check breaking behavioral changes from a specific version
istioctl x precheck --from-version 1.25.0
```

### Step 2: Install Canary Control Plane
```bash
# Download and use the NEW version istioctl binary
./istioctl install --set revision=1-26-3 -y
```

Verify two `istiod` pods are running side-by-side:
```bash
kubectl get po -n istio-system -l app=istiod
```
*Output:*
```
NAME                                   READY   STATUS    RESTARTS   AGE
istiod-1-25-0-864b9777f7-r98pl         1/1     Running   0          10d
istiod-1-26-3-67bc786997-2xx4b         1/1     Running   0          2m
```

### Step 3: Upgrade Gateways (Side-by-Side vs. In-Place)
By default, `istio-ingressgateway` upgrades in-place if you re-apply the manifest. For a safe canary gateway upgrade:

1. Duplicate gateway deployment YAML with revision label `istio.io/rev: 1-26-3`.
2. Apply the canary gateway. Both gateways will share the K8s Service selector and load-balance incoming traffic.
3. Test canary gateway, then delete the old gateway deployment.

### Step 4: Migrate Workloads (Namespace Relabeling vs. Revision Tags)

#### Method A: Direct Namespace Relabeling (Manual)
> ⚠️ **CRITICAL EXAM RULE:** You MUST remove `istio-injection=enabled` when using `istio.io/rev`. `istio-injection` takes precedence and ignores `istio.io/rev`!

```bash
# 1. Remove legacy injection label
kubectl label namespace default istio-injection-

# 2. Add revision label
kubectl label namespace default istio.io/rev=1-26-3 --overwrite

# 3. Restart deployments to inject new proxy version
kubectl rollout restart deployment -n default
```

#### Method B: Revision Tags (`istioctl tag`) — **RECOMMENDED FOR EXAM**
Revision tags decouple namespace labeling from specific version numbers.

```bash
# 1. Initially set stable tag on old version
istioctl tag set prod-stable --revision 1-25-0

# 2. Label namespace using the TAG alias (NOT version number!)
kubectl label namespace default istio-injection-
kubectl label namespace default istio.io/rev=prod-stable --overwrite

# 3. Test new revision on a canary namespace first
istioctl tag set prod-canary --revision 1-26-3
kubectl label namespace test-ns istio.io/rev=prod-canary --overwrite
kubectl rollout restart deployment -n test-ns

# 4. Once validated, point the STABLE tag to the NEW revision in ONE command!
istioctl tag set prod-stable --revision 1-26-3 --overwrite

# 5. Restart workloads in all prod-stable namespaces
kubectl rollout restart deployment -n default
```

### Step 5: Verify Proxy Status
```bash
# Check control plane to proxy version mapping across mesh
istioctl proxy-status

# Verify specific pod proxy version
istioctl version
```

### Step 6: Purge Old Control Plane
```bash
# Cleanly remove the old revision control plane
istioctl uninstall --revision 1-25-0 -y
```

## 4. Risk Mitigation & Compatibility Flags

### Compatibility Versions (`--set compatibilityVersion`)
If upgrading to a new Istio version introduces new default behavior (e.g., stricter telemetry or changed header processing) that might break legacy applications, use `compatibilityVersion`:

```bash
# Install Istio 1.26 control plane, but force it to preserve 1.25 behavior defaults:
istioctl install --set revision=1-26-3 --set compatibilityVersion=1.25.0 -y
```

* **Why use this?** Allows you to upgrade security patches and control plane binaries immediately while deferring breaking behavioral config updates until application teams are ready.

## 5. Top 5 ICA Exam "Gotchas" & Troubleshooting Tips

### 1. Label Precedence Conflict
* **Question:** *"I labeled a namespace with `istio.io/rev=1-26-3`, but pods are still injected with `1.25.0`!"*
* **Root Cause:** The namespace still has `istio-injection=enabled`.
* **Fix:** `kubectl label namespace <ns> istio-injection-`

### 2. Revision Tag Alias Disconnect
* **Question:** *"How to migrate 50 namespaces to a new Istio revision without relabeling each namespace individually?"*
* **Fix:** Use revision tags! Move the tag target:
  `istioctl tag set prod-stable --revision 1-26-3 --overwrite`

### 3. Verification Command Missing
* **Question:** *"How do you prove that a workload is connected to the new control plane?"*
* **Fix:** Run `istioctl proxy-status` or inspect pod annotations:
  `kubectl get pod <pod> -o jsonpath='{.metadata.annotations.istio\.io/rev}'`

### 4. Rollback Plan
* **Question:** *"The canary revision is failing in production. How do you roll back instantly?"*
* **Fix (if using Revision Tags):**
  `istioctl tag set prod-stable --revision 1-25-0 --overwrite`
  `kubectl rollout restart deployment -n <ns>`
* **Fix (if using Revision Labels):**
  `kubectl label namespace <ns> istio.io/rev=1-25-0 --overwrite`
  `kubectl rollout restart deployment -n <ns>`

### 5. Cleaning Up Old Revisions
* **Question:** *"How do you safely remove an old revision without deleting user workloads or gateways?"*
* **Fix:** Use `istioctl uninstall --revision <old-rev>` instead of `kubectl delete ns istio-system`!
